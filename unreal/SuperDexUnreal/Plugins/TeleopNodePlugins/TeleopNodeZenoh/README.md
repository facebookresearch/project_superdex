# TeleopNodeZenoh

A SuperDex Teleop backend over [zenoh](https://zenoh.io), in one module, `TeleopNodeZenoh`:

- `UTeleopNodeImplZenoh`, the TeleopNode backend. Messages are protobuf (`Source/TeleopNodeZenoh/Private/TeleopMsgs`), encoded with [nanopb](https://github.com/nanopb/nanopb), whose C runtime is compiled into the module.
- `FZenohSession`, `FZenohPublisher` and `FZenohSubscriber`: zenoh sessions, publishers and subscribers over [zenoh-pico](https://github.com/eclipse-zenoh/zenoh-pico), also compiled from source into the module.

| Path | Contents |
| --- | --- |
| `Source/TeleopNodeZenoh/Private/TeleopMsgs/teleop.proto` | The wire contract: `DoubleArray` and `PoseArray` in package `superdex.teleop.v1`. Any protobuf implementation can read and write them. |
| `Source/TeleopNodeZenoh/Private/TeleopMsgs/teleop_codec.h` | Header-only nanopb encode/decode straight from and into caller-owned arrays, with no size caps. No engine types, so robot-side C++ can use it too. |
| `Source/TeleopNodeZenoh/Private/TeleopMsgs/generated/` | `teleop.pb.c/.h` generated by nanopb from `teleop.proto`. |

## Getting zenoh-pico and nanopb

The modules compile zenoh-pico and nanopb's C runtime from source, so both must be placed into the
plugin before Unreal builds it. The SuperDexUnreal project's `hydrate_plugins.py` does that along
with the other plugins' native libraries; on its own, configuring this directory with CMake does it:

```bash
cmake -S Plugins/TeleopNodePlugins/TeleopNodeZenoh -B <build directory>
```

It downloads both at pinned commits, applies the patches in `ThirdParty/zenoh-pico/patches` (Android
API levels below 28, clang-cl on Windows) and places zenoh-pico in `Source/TeleopNodeZenoh/Private/ZenohPico`
and nanopb in `Source/TeleopNodeZenoh/Private/Nanopb`. Re-running it leaves unchanged files alone.

| Library | Version | Override with |
| --- | --- | --- |
| zenoh-pico | 1.10.1 | `SUPERDEX_ZENOH_PICO_SOURCE_DIR` (an already patched tree) or `SUPERDEX_ZENOH_PICO_GIT_REPOSITORY` (a mirror) |
| nanopb | 0.4.9.1 | `SUPERDEX_NANOPB_SOURCE_DIR` or `SUPERDEX_NANOPB_GIT_REPOSITORY` |

zenoh-pico is configured with `Z_FEATURE_LOCAL_SUBSCRIBER=1`, so publishers and subscribers in one
process see each other. The same CMake project also provides `TeleopNodeZenoh::teleop_msgs`
(`teleop.pb.c/.h`, `teleop_codec.h` and nanopb) and `zenohpico::lib` for code outside Unreal, such
as the robot side: `add_subdirectory` this directory and link them.

## Using it

Enable the plugin in your project (it is off by default). Then either make it the project's default,
for every TeleopNode with an empty `CommunicationClassName`, under **Project Settings › Plugins ›
SuperDex Teleop › Default Communication Class Name**, or set it on each TeleopNode component (operator
and robot):

```
CommunicationClassName = /Script/TeleopNodeZenoh.TeleopNodeImplZenoh
```

## Settings

**Project Settings › Plugins › Teleop Node Zenoh**: session, publishers and subscribers. The session opens when the first TeleopNode starts and closes when the last one stops, so changed settings apply from the next Play without restarting the Editor or game. The logs are helpful for identifying what was configured (after Play):

```
LogZenoh: Display: Zenoh session open (mode peer, connect [], listen 'tcp/127.0.0.1:7447', scouting off)
```

On a packaged build, you can also override the session settings from the command line:

```
-ZenohMode=peer -ZenohListen=tcp/0.0.0.0:7447 -ZenohScouting=false
-ZenohMode=client -ZenohConnect=tcp/192.168.1.20:7447
```

On Android, put them in `UECommandLine.txt`, or, in a non-Shipping build, set them over adb as shown
in [Android headset over USB](#configuration-for-an-android-headset-over-usb-adb-reverse).

Teleop publishers default to priority `InteractiveHigh`, express (no batching) and congestion control `Drop`. Each subscriber keeps only the newest sample (`SubscriberQueueDepth = 1`).

## Choosing a setup

| Setup | Router? | Mode | Listen Endpoint | Connect Endpoints |
| --- | --- | --- | --- | --- |
| Everything in one process | No | Peer | `tcp/127.0.0.1:7447` | empty |
| Unreal + one other process or machine | No | Peer | one side: `tcp/0.0.0.0:7447` | other side: `tcp/<listener-ip>:7447` |
| Three or more processes, or any number of clients | Yes (`zenohd`) | Client | (not used) | `tcp/<router-ip>:7447` |

Turn **Multicast Scouting** off whenever you set endpoints explicitly. Scouting can pick the wrong network adapter on machines with virtual adapters (WSL, Hyper-V).

### Configuration for single-process (no router)

```ini
[/Script/TeleopNodeZenoh.TeleopNodeZenohSettings]
Mode=Peer
ListenEndpoint=tcp/127.0.0.1:7447
bMulticastScouting=False
```

- Every TeleopNode in the process shares one session. Messages between them stay in memory.
- zenoh-pico won't open a peer session without a listen endpoint. Loopback keeps it off the network. Use another port if 7447 is taken.
- `/Script/SuperDexTeleop.TeleopNodeImplDirect` is an alternative for a single process: it passes messages in memory without zenoh.

### Configuration for peer-to-peer

Strictly two peers. One side listens and the other connects. Both must be in peer mode.

```ini
; listening side
[/Script/TeleopNodeZenoh.TeleopNodeZenohSettings]
Mode=Peer
ListenEndpoint=tcp/0.0.0.0:7447
bMulticastScouting=False

; connecting side
[/Script/TeleopNodeZenoh.TeleopNodeZenohSettings]
Mode=Peer
+ConnectEndpoints=tcp/192.168.1.20:7447
bMulticastScouting=False
```

### Configuration for an Android headset over USB (adb reverse)

Runs one peer in an app on the headset and the other on the PC, connected through the USB cable. The PC side listens on loopback, and the headset connects to its own loopback, which `adb reverse` carries to the PC.

1. With the headset connected over USB, forward the port and check that it is listed:

   ```
   adb reverse tcp:7447 tcp:7447
   adb reverse --list
   ```

2. Point the headset app at it, without repackaging. A non-Shipping build appends the
   `debug.ue.commandline` property to its command line at launch. For example in PowerShell:

   ```powershell
   adb shell "setprop debug.ue.commandline '-ZenohMode=peer -ZenohConnect=tcp/127.0.0.1:7447 -ZenohScouting=false'"
   adb shell getprop debug.ue.commandline
   ```

   `getprop` should print the three options as one line.

3. On the PC, listen on loopback and press Play before launching the app (the headset connects once,
   when its session opens):

   ```ini
   [/Script/TeleopNodeZenoh.TeleopNodeZenohSettings]
   Mode=Peer
   ListenEndpoint=tcp/127.0.0.1:7447
   bMulticastScouting=False
   ```

4. Launch the app on the headset and check its log:

   ```
   adb logcat -s UE | findstr "LogZenoh LogTeleopZenoh"
   ```

   It should report `connect [tcp/127.0.0.1:7447]`. Error -102 means nothing was listening on the PC
   yet: start Play, then relaunch the app.

Unplugging the headset or restarting the adb server removes the forward, and rebooting the headset clears the property. To undo both:

```powershell
adb reverse --remove tcp:7447
adb shell "setprop debug.ue.commandline ''"
```

### Configuration for using a router (zenohd)

```ini
[/Script/TeleopNodeZenoh.TeleopNodeZenohSettings]
Mode=Client
+ConnectEndpoints=tcp/192.168.1.20:7447
bMulticastScouting=False
```

**Windows router:** `zenohd`'s default listener (`tcp/[::]:7447`) may only accept IPv6, so IPv4 clients (including `127.0.0.1`) fail with error -102. Start it with `zenohd -l tcp/0.0.0.0:7447 -l tcp/[::]:7447`.

## Troubleshooting

| Log | Meaning |
| --- | --- |
| `Failed to open zenoh session ... (error -102)` | Nothing accepted the connection: router or peer not running, wrong address, firewall, or the Windows IPv4 listener issue above. Check with `Test-NetConnection <ip> -Port 7447`. |
| `Peer mode needs a listen endpoint ...` | Peer mode with no endpoints. |
| `No zenoh session (see LogZenoh errors)` | The session failed to open; look for the first `LogZenoh` error. |
| `Could not decode N bytes on <key>` | The sender's message isn't a `DoubleArray`/`PoseArray` from `teleop.proto`. |

If other machines connect to a listening Windows machine (router or peer), allow TCP 7447 through Windows Firewall.

## Changing the messages

1. Edit `teleop.proto`, and update `teleop_codec.h` if a message changed shape.
2. Regenerate `generated/` with nanopb 0.4.9.1, from `Source/TeleopNodeZenoh/Private/TeleopMsgs`:
   `nanopb_generator.py -D generated teleop.proto`.
