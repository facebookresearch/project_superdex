# Tactile Sensors

SuperDex exposes tactile readings through concrete representations. A producer
may emit any representation directly, and downstream code can transform it
without depending on a particular policy or training framework.

| Representation | Description | Reference implementation |
|---|---|---|
| Vertex forces | Dense per-vertex force vectors | `SensorLinkVertexForce` |
| Aggregate force or wrench | Values aggregated across one tactile site | `AggregateTactileForce` or `AggregateTactileWrench` |
| Rectangular force grid | A regular spatial grid | `MapTactileHemisphereToRect` |

The aggregate-force baseline sums per-vertex forces without applying a learned
response, calibration, or threshold. Aggregate wrench also sums moments about an
explicit reference point. The C++ aggregation functions are public and do not
require a graph; `SensorAggregateForce` computes the aggregate force as a graph
sensor.

See [Sensor Graphs](./sensor_graphs.mdx) for source acquisition, dependency wiring,
and timestamped observation reads.

## Available tactile sensors

These graph sensors are registered in the public `RoboticsContext`. The first two
read contact from a link; the next two transform a vertex-force input; the last
acquires contact itself and applies a fingertip model.

1. **`SENSOR_LINK_CONTACT_FORCE`**: the total contact force `[3]` on a link, in
   newtons, acting from the environment on the link and expressed in the sensor
   frame. It includes every contact on the link and gives no spatial
   distribution. `sampleRateHz: 0` captures every graph step; a positive rate
   follows its own drift-free schedule.
2. **`SENSOR_LINK_VERTEX_FORCE`**: one force vector per surface vertex, `[N, 3]`,
   in the sensor link frame, with vertex positions and normals in
   `VertexListMeta`. Use it when contact location matters, and as the input to
   the two transforms below. It takes the same `sampleRateHz` parameter.
3. **`SENSOR_AGGREGATE_FORCE`**: the sum `[3]` of one vertex-force input. It
   keeps the input's capture time and does not query physics, so it reports
   only what its input saw; use the link contact force for the link's net
   physical contact.
4. **`SENSOR_SEED_RECT_MAP`**: a rectangular `[height, width, 3]` force grid from
   a vertex-force input and its vertex metadata, using the hemisphere mapping
   described [below](#mapping-a-hemispherical-sensor-to-a-rectangle). Configure
   the hemisphere center and directions for the actual sensor geometry.
5. **`SENSOR_SEED_V1_MLP`** (experimental): a SEED fingertip response `[3]`. It
   reads the link's contact points itself, then applies a learned model when
   `weightsPath` supplies weights; with no weights, or `bypassModel: true`, it
   publishes the raw contact force.

Contact-based sensors require the link's actor to support their force queries.
The vertex-force source also requires an integration method whose final stage is
the end of the physics step; incompatible methods are rejected instead of
returning a mistimed observation.

A typical tactile pipeline declares a vertex-force source on the fingertip link
and selects a map, an aggregate, or both, as shown in
[Sensor Graphs](./sensor_graphs.mdx#declaring-a-pipeline-on-a-bot).

## Vertex-force layout contract

A `TactileTaxelLayout` contains ordered vertex positions in the sensor link
frame. The order defines vertex identity. A graph consumer that requires the
geometry obtains the producer-owned `VertexListMeta` through
`TryGetSensorMetadata<VertexListMeta>()` during initialization.

Vertex-force observations contain one sensor-link-frame force vector for every
layout entry. Taxels with no reported contact have a valid zero force. Sparse
node-force records with the same index are accumulated.

## Reading Mochi node forces

Mochi computes node-force queries during a simulation step. Register the query
before stepping, keep the handle while reading, and cancel it when the consumer
is done.

```cpp
Error error;
TactileTaxelLayout layout = MakeTactileTaxelLayout(taxelPositions, error);
QueryHandle query = actor->RegisterQuery(QueryType::NodeContactForces, error);

// Step the scene before the first read.
TactileTaxelForces taxelForces =
    ReadTactileTaxelForces(actor, actor->GetRootTransform(), layout, error);
TactileAggregateForce aggregateForce = AggregateTactileForce(taxelForces, error);

actor->CancelQuery(query);
```

`taxelForces.forces` and `aggregateForce.force` are expressed in newtons in the
supplied sensor-link frame. Supplying the frame explicitly also supports sensors whose
frame is offset from their actor; use the actor root transform when the two
frames coincide.

The corresponding C++ entry points are `MakeTactileTaxelLayout`,
`ReadTactileTaxelForces`, and `AggregateTactileForce` in
`superdex_robotics/sensors/tactile_observation.h`.

## Supplying a layout

The producer does not guess which mesh represents a sensor. Applications must
provide the stable, ordered taxel positions that correspond to the actor's node
indices. This keeps the public API independent of a particular sensor asset and
makes the same reader usable for simulated and externally sourced layouts.

The fixed output shape and `VertexListMeta` are validated when the graph is
built. They remain producer-owned and immutable for that sensor instance.

## Mapping a hemispherical sensor to a rectangle

`MapTactileHemisphereToRect` maps ordered taxel positions and forces onto a
row-major rectangular force grid. Configure the hemisphere center, the
center-to-tip direction, a tangent direction for zero longitude, and the grid
shape:

```cpp
TactileHemisphereRectParams params{
    .center = hemisphereCenterSensorLink,
    .tipDirection = {0_r, 0_r, 1_r},
    .zeroLongitudeDirection = {1_r, 0_r, 0_r},
    .width = 16,
    .height = 8,
    .rasterization = TactileRectRasterizationType::ConservativeVoronoi,
    .voronoiOversampling = 4,
};
TactileForceGrid grid =
    MapTactileHemisphereToRect(layout, taxelForces, params, error);
```

For repeated frames with one layout, resolve the projection once with
`BuildTactileRectProjection`, then pass each vertex-force observation to
`RasterizeTactileRectProjection`. C++ callers that also preallocate the
output use `RasterizeTactileRectProjectionInto`; it retains the output storage
and does not repeat the projection or Voronoi work.

The default equal-area projection places the tip at continuous coordinate
`(0, 0)`, at the intersection of the four central cells for an even grid. It
maps the configured spherical cap through a disk into the full rectangle.
Equidistant and octahedral projections are also available.

The default conservative Voronoi rasterization resolves ownership on a support
grid whose linear dimensions are `voronoi_oversampling` times the requested
output dimensions. It distributes each taxel force across its support region,
then sum-downsamples into the output grid. The cached contribution weights for
each selected taxel sum to one, so the rectangular-grid force sum equals the
selected taxel-force sum. A 64-by-64 grid with the default factor of four
uses a 256-by-256 support map while retaining a 64-by-64 runtime observation.

Set `rasterization` to `TactileRectRasterizationType.NEAREST_CELL` for the
sparse compatibility representation in which every taxel contributes its
complete force to one nearest output cell. `grid.taxel_counts` reports how many
source taxels contribute to each output cell in either mode.

For a SEED-shaped sensor, pass the hemisphere center from the sensor geometry
and choose the tip and zero-longitude directions from the sensor link axes. No
learned response or sensor-specific calibration is applied by the mapper.
