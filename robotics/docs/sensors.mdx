# Sensors

A sensor turns simulation state into a numeric observation. Some sensors
**query the SuperDex scene** directly: the joint positions and velocities of a
bot, the total contact force on a link, the force at each vertex of a link's
surface, or the wrench through each joint of an articulation. Others
**transform the output of other sensors**: they sum or map surface forces, stack
several signals, or model the observation path with noise, outliers and delay.
Sources and transforms share one interface, so a transform can consume a source
or another transform.

Sensors are connected by a **`SensorGraph`**: a directed acyclic graph whose
edges are declared inputs. Each graph step runs the outputs you select and their
upstream dependencies, in dependency order, after physics has produced the data
to measure. A sensor is either **bot-level**, declared on one of a bot's links
and owned by that bot, or **scene-level**, declared in the scene and bound to no
link. A scene-level sensor combines or post-processes bot sensors, which it
names in full as `bot/link/sensor`.

Sensors, and the graph that connects them, are specified **declaratively** or
**programmatically**. Declaratively, a link's `sensors` list in a
`.superdex_bot` file declares bot-level sensors, and the top-level `sensors`
list in a `.superdex_scene` file declares scene-level ones; loading the scene
builds the graph from both. Parameters are inline JSON or a path to a
`.superdex_sensor` file. Programmatically, `create_sensor` on the
`RoboticsContext` or on a bot creates a sensor at runtime, from C++ or Python,
and C++ can also assemble a `SensorGraph` directly. See
[Making a Sensor](./making_a_sensor.mdx) to add a new type.

**Ownership.** The `RoboticsContext` owns every sensor; the graph only uses
them. A bot-level sensor is destroyed with its bot, and BotScene first removes
it and everything downstream of it from the graph. A scene-level sensor
declared in a scene lives as long as the scene, and one you create on the
context lives until you destroy it or the context is torn down. Reading the
latest sample in C++ returns a borrowed view: consume or copy it before the
sensor publishes again, resets or is destroyed. Python's `copy_latest_values()`
returns an owning copy. See [Bot Context & Lifetime](./bot_context_lifetime.mdx)
for the ownership of bots and their components.

## Sensor Types

| Sensor | Category | Description |
|---|---|---|
| `SENSOR_LINK_CONTACT_FORCE` | [Tactile](./tactile_observations.mdx) | Total contact force on a link. |
| `SENSOR_LINK_VERTEX_FORCE` | [Tactile](./tactile_observations.mdx) | Contact force at each vertex of a link's surface. |
| `SENSOR_AGGREGATE_FORCE` | [Tactile](./tactile_observations.mdx) | Transform: the sum of a vertex-force input. |
| `SENSOR_SEED_RECT_MAP` | [Tactile](./tactile_observations.mdx) | Transform: a rectangular force map from a hemispherical vertex-force input. |
| `SENSOR_SEED_V1_MLP` | [Tactile](./tactile_observations.mdx) | Experimental SEED fingertip response, with an optional learned model. |
| `SENSOR_JOINT_ENCODER` | [Joint Pose and Wrench](./joint_pose_and_wrench.mdx) | Positions and velocities of a bot's articulated links. |
| `SENSOR_ARTICULATED_JOINT_WRENCH` | [Joint Pose and Wrench](./joint_pose_and_wrench.mdx) | Force and torque through each joint of an articulation. |
| `SENSOR_CONCAT` | [Signal processing](./sensor_graphs.mdx#combining-outputs) | Several equally shaped outputs stacked into one. |
| `SENSOR_GAUSSIAN_NOISE` | [Signal processing](./sensor_graphs.mdx#noise-delay-and-history) | Zero-mean Gaussian noise, drawn once per input publication. |
| `SENSOR_UNIFORM_NOISE` | [Signal processing](./sensor_graphs.mdx#noise-delay-and-history) | Additive uniform noise, drawn once per input publication. |
| `SENSOR_OUTLIER_INJECTION` | [Signal processing](./sensor_graphs.mdx#noise-delay-and-history) | Whole samples replaced by outliers at a fixed probability. |
| `SENSOR_DELAY_LINE` | [Signal processing](./sensor_graphs.mdx#noise-delay-and-history) | Its input, released after a fixed delay. |
| `SENSOR_TEMPORAL_WINDOW` | [Signal processing](./sensor_graphs.mdx#noise-delay-and-history) | A rolling history of its input; C++ registration required. |
| `SENSOR_CAMERA` | Camera | Camera pose and intrinsics for a renderer. It does not publish images and is not a sensor-graph node. |

All except `SENSOR_TEMPORAL_WINDOW` are registered in the public
`RoboticsContext`. To add your own type, see
[Making a Sensor](./making_a_sensor.mdx).
