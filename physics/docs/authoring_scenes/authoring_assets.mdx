# Authoring Assets

The SuperDex Physics engine provides utilities to convert geometry data into simulation-ready model assets. The core model-data workflow loads and validates geometry, optionally converts its length units and axis convention, optionally bakes a grid-interpolated signed-distance field (SDF) for use in the [Contact](../concepts/contact.md) formulation, and saves the result as a `.mochi.h5` file. [Experimental mesh generation](#generate-a-tetrahedral-volume) additionally uses the separately installed geometry helper.

Supported inputs are:

- Wavefront OBJ (`.obj`)
- STL (`.stl`)
- Stanford PLY (`.ply`)
- Object File Format (`.off`)
- SuperDex Physics JSON (`.mochi.json`)
- SuperDex Physics HDF5 (`.mochi.h5`)

The OBJ, STL, PLY, and OFF loaders mentioned above import only triangulated surface geometry; loading a surface file does not generate a tetrahedral volume. Use the [experimental mesh-processing module](#generate-a-tetrahedral-volume) or another mesher to generate tetrahedra, or create a polyline directly from nodes and connectivity. Construct [`MeshData`](pathname:///generated/api/latest/cpp/structsuperdex_1_1MeshData.html) from those arrays (as described in [Mesh Shapes](../concepts/shapes.mdx#mesh-shapes)) and assign it to [`ModelData.mesh`](pathname:///generated/api/latest/cpp/structsuperdex_1_1ModelData.html).
Set [`nodesPerElement`](pathname:///generated/api/latest/cpp/structsuperdex_1_1MeshData.html) / [`nodes_per_element`](pathname:///generated/api/latest/python/api/physics.html#superdex.physics.MeshData.nodes_per_element) to `2` for polylines, `3` for triangles, or `4` for tetrahedra.
The [Mass on Rod Spring](../examples/tendons_rods/mass_on_rod_spring.md) and [high-fidelity rod-based tendon](../examples/tendons_rods/tendon_model_fidelity.md#high-fidelity-elastic-rod) examples provide practical polyline-model references.
For higher-level asset preparation, use the [SuperDex Studio Model Editor](https://projectsuperdex.com/studio/docs/latest/model_editor/) before starting this workflow.

## Preparing STEP and Tetrahedral Meshes

STEP (`.step` / `.stp`) is CAD geometry, not a runtime Physics model format. Prepare it in Studio, then load the resulting mesh asset with the Physics APIs below:

1. **Tessellate the CAD surface.** Studio's CAD source processing converts STEP faces into a triangle mesh. It can use authored face colors to control local mesh density, preserving more detail where contact needs it.
2. **Choose surface or volume geometry.** A triangle surface can represent a rigid body or articulated link. A soft body requires a tetrahedral volume; Studio's **Tetrahedralize** operation fills a closed, self-intersection-free surface with tetrahedra. Its constrained variant preserves the boundary shape, while the refinement variant may approximate it.
3. **Export the prepared Physics model.** Load it as `ModelData` or a shape, then configure the actor's material and contact behavior. Mesh generation does not itself make a body soft: the consuming actor type determines that behavior.

The model-data loaders below do not tessellate STEP or generate tetrahedra. Keep CAD preparation in the [Model Editor](https://projectsuperdex.com/studio/docs/latest/model_editor/) or your own meshing pipeline. For a prepared triangle surface, the Python mesh module provides a volume-generation alternative.

### Generate a Tetrahedral Volume

R2 Physics wheels include `superdex.physics.mesh`, which provides experimental surface remeshing and tetrahedralization. Heavy mesh operations require the separately installed `superdex-mesh-cli` helper distribution. The module discovers its packaged executable automatically; `SUPERDEX_MESH_CLI_PATH` can instead point to a local helper executable. If no helper is available, these operations report an error.

For a closed triangle surface free of self-intersections:

```python
import numpy as np
import superdex.physics as sdp
import superdex.physics.mesh as mesh

surface_model = sdp.model.load_from_file("models/closed_surface.obj")
surface = surface_model.mesh
vertices, tetrahedra = mesh.tetrahedralize(
    vertices=np.asarray(surface.coordinates).reshape(-1, 3),
    faces=np.asarray(surface.connectivity, dtype=np.int32).reshape(-1, 3),
)
model_data = sdp.ModelData()
model_data.mesh = sdp.MeshData(
    nodes_per_element=4,
    coordinates=vertices.reshape(-1),
    connectivity=tetrahedra.reshape(-1),
)
sdp.model.validate(model_data)
```

Continue with the validation, coordinate conversion, and serialization steps below. `tetrahedralize` may approximate the input boundary. `tetrahedralize_constrained`, with `ConstrainedTetrahedralizationParams`, preserves its shape but may split boundary triangles; setting the parameter object's `strict` property to `True` requires the original boundary triangles to remain unchanged. The constrained input must also be a consistently oriented manifold with no unreferenced or coincident vertices. These mesh-generation APIs are experimental; they do not change the runtime actor's material or contact settings.

## Input Requirements

The model-data loading and validation APIs do not repair or remesh geometry. Prepare input data with these requirements in mind:

- Coordinates must reach simulation in the consuming application's length units and axis convention. Input data in another convention can be transformed with [Convert Scale and Coordinate Space](#convert-scale-and-coordinate-space). For a known consumer, author assets in that consumer's expected length units and axis convention to minimize friction.
- A meaningful SDF requires a suitable closed surface with consistent orientation and without severe degeneracies, self-intersections, or ambiguous topology.

Checked loading and model validation enforce the invariants known to the model API. Autocorrection applies only narrowly limited in-place fixes, such as normalizing applicable vectors and weights.

See [Shapes](../concepts/shapes.mdx#model-data) for model and shape representations, and [Collider Representations](../concepts/contact.md#collider-representations) for how a baked SDF is used at runtime.

## Convert Scale and Coordinate Space

If loaded data does not already use the consuming application's convention, bake the conversion into the model before generating an SDF or saving the asset. Define the source and target [`CoordinateSpace`](pathname:///generated/api/latest/cpp/structsuperdex_1_1CoordinateSpace.html) values from the asset pipeline and consuming application, respectively. ## Bake a Grid SDF

`model_utils::BakeSdf()` / [`sdp.model.bake_sdf()`](pathname:///generated/api/latest/python/api/models.html#superdex.physics.model.bake_sdf) computes a grid SDF from triangle or tetrahedral mesh data and stores it in [`ModelData::sdf`](pathname:///generated/api/latest/cpp/structsuperdex_1_1ModelData.html) / `model_data.sdf`, replacing any SDF already there. The operation may be slow and memory intensive, and it does not condition or repair the source mesh.

Grid generation is controlled by `GridSdfParams` ([C++](pathname:///generated/api/latest/cpp/structsuperdex_1_1GridSdfParams.html), [Python](pathname:///generated/api/latest/python/api/physics.html#superdex.physics.GridSdfParams)):

- `resolutionMode` / `resolution_mode` selects the model measurement used to derive grid cell size, or selects explicit grid cell sizing.
- `resolutionDelta` / `resolution_delta` is a per-axis multiplier in derived modes. In explicit mode, it is the maximum grid cell size in the model's length units.
- `boundaryPaddingDist` / `boundary_padding_dist` expands the model bounds in the model's length units so queries remain valid outside the surface.
- `minGridResolution` / `min_grid_resolution` sets the minimum number of grid cells per axis.

The defaults derive grid cell size from mean edge length. They are useful as a starting point, but production assets should select these parameters deliberately. Increasing [`resolutionDelta`](pathname:///generated/api/latest/cpp/structsuperdex_1_1GridSdfParams.html) / [`resolution_delta`](pathname:///generated/api/latest/python/api/physics.html#superdex.physics.GridSdfParams.resolution_delta) creates larger cells, reducing detail, memory use, and generation time. Decreasing it preserves finer detail at sharply increasing memory and generation cost, approximately cubic in linear resolution. Choose a resolution based on the asset's physical scale, smallest relevant features, intended contact behavior, and available memory.

```cpp
if (!modelData.mesh ||
    (modelData.mesh->nodesPerElement != 3 && modelData.mesh->nodesPerElement != 4)) {

  return;
}

superdex::GridSdfParams params{};
superdex::model_utils::BakeSdf(
    modelData, params, superdex::ErrorAssert{});

  // Report that SDF baking did not produce grid data.
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
if model_data.mesh is None or model_data.mesh.nodes_per_element not in (3, 4):

params = sdp.GridSdfParams()
sdp.model.bake_sdf(model_data, params)

if model_data.sdf is None or len(model_data.sdf.values) == 0:
    raise RuntimeError("SDF baking did not produce grid data.")
```

## Save a `.mochi.h5` Asset

Pass the HDF5 format explicitly when saving:

<Tabs groupId="language">
<TabItem value="cpp" label="C++" default>

```cpp
constexpr char const* outputPath = "generated/prepared_part.mochi.h5";
superdex::model_utils::SaveToFile(
    modelData,
    outputPath,
    superdex::FileFormat::H5,
    superdex::ErrorAssert{});
```

</TabItem>
<TabItem value="python" label="Python">

```python
output_path = "generated/prepared_part.mochi.h5"
sdp.model.save_to_file(model_data, output_path, sdp.FileFormat.H5)
```

</TabItem>
</Tabs>

`FileFormat::H5` / [`sdp.FileFormat.H5`](pathname:///generated/api/latest/python/api/physics.html#superdex.physics.FileFormat) selects the serializer; the filename alone does not. Missing destination directories are created automatically. The saved model contains the model's mesh data and the baked SDF. `model_utils::SaveToFile()` / [`sdp.model.save_to_file()`](pathname:///generated/api/latest/python/api/models.html#superdex.physics.model.save_to_file) serializes the supplied data without implicitly autocorrecting or validating it.

Do not blindly overwrite a richer source asset. Some existing model files contain data for unsupported or experimental features that the public [`ModelData`](pathname:///generated/api/latest/cpp/structsuperdex_1_1ModelData.html) representation cannot preserve when resaved.

## Verify the Result

Reload the output through the same standalone model-data API and confirm that both data sets survived serialization:

<TabItem value="cpp" label="C++" default>

```cpp
superdex::ModelData savedModel = superdex::model_utils::LoadFromFile(
    outputPath, superdex::ErrorAssert{});

if (!savedModel.mesh || !savedModel.sdf || savedModel.sdf->values.empty()) {
  // Report that the saved asset is missing mesh or SDF data.
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
saved_model = sdp.model.load_from_file(output_path)

if saved_model.mesh is None:
    raise RuntimeError("The saved asset does not contain mesh data.")
if saved_model.sdf is None or len(saved_model.sdf.values) == 0:
    raise RuntimeError("The saved asset does not contain SDF data.")
```

Loading the finished asset as a runtime physics shape is covered in [Shapes](../concepts/shapes.mdx#loading-from-files).

These model-data operations do not require initialization or shutdown. Context initialization is needed when registering runtime shapes and constructing scenes, not when preparing and serializing model data.
